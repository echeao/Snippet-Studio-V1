## 2. 数据模型

### 2.1 领域模型 Snippet

**源文件：** `model/Snippet.kt`

```kotlin
data class Snippet(
    val id: String,           // 唯一标识 "s_{timestamp}_{uuid4}"
    val type: SnippetType,    // 类型枚举
    val title: String,        // 标题
    val fileName: String,     // 物理文件名
    val content: String,      // 正文内容
    val tags: List<String>,   // 标签列表
    val starred: Boolean,     // 是否收藏
    val createdAt: Long,      // 创建时间戳 (ms)
    val updatedAt: Long,      // 修改时间戳 (ms)
    val sizeBytes: Int,       // 内容字节数
    val folder: String,       // 所属文件夹相对路径
    val trashed: Boolean,     // 是否在回收站
    val trashedAt: Long?      // 入站时间戳
)
```

**计算属性：**

| 属性 | 算法 |
|------|------|
| `displayTitle` | 若 title 为空则取 fileName 去扩展名 |
| `defaultFileName` | title → 过滤非法字符 → 截断 20 字符 → 拼接类型扩展名 |

**SnippetType 枚举：**

| 枚举值 | code | 扩展名 | 匹配规则 |
|--------|------|--------|----------|
| HTML | `html` | `.html` | .html, .htm |
| JS | `js` | `.js` | .js, .jsx, .ts, .tsx |
| MARKDOWN | `markdown` | `.md` | .md, .markdown |
| PROMPT | `prompt` | `.txt` | 其他所有 |

### 2.2 数据库实体

## 4. 核心模块实现

### 4.1 SnippetRepository

**源文件：** `data/repo/SnippetRepository.kt`

**职责：** 统筹三端数据源联动的核心业务仓库。

**三端原子写入协议（以 create 为例）：**

```
步骤 1: snippetDao.upsert(entity)              → Room DB
步骤 2: LocalFileManager.writeSnippetToFile()  → 物理文件 (IO 线程)
步骤 3: gitManager.writeSnippetFile()          → Git 沙盒
```

**关键方法清单：**

| 方法 | 三端操作 |
|------|----------|
| `create()` | DB upsert + 物理写入 + 沙盒写入 |
| `saveOrUpdate()` | DB upsert + 物理写入 + 沙盒写入 |
| `trash()` | DB trash + 物理移入 .trash + 沙盒删除 |
| `restore()` | DB restore + 物理从 .trash 恢复 + 沙盒写入 |
| `purge()` | DB purge + 物理从 .trash 删除 + 沙盒删除 |
| `updateRename()` | 清理旧文件残留 + saveOrUpdate |
| `updateFolder()` | 清理旧路径残留 + saveOrUpdate |
| `exportAllToGit()` | DB 全量导出至沙盒 + cleanDeletedFiles |
| `syncWithLocalRepository()` | 物理→DB 全量扫描同步 |
| `syncAllToPhysicalStorage()` | DB→物理 全量回写 + 远端删除清理 |

### 4.2 LocalFileManager

**源文件：** `util/LocalFileManager.kt`

**职责：** SAF/Local 双模式物理文件操作。

**双模式路由逻辑：**
```
if (repoTreeUriStr 非空) {
    → SAF 模式：DocumentFile.fromTreeUri() 操作
} else {
    → 本地模式：java.io.File 操作 getDefaultRepoDir()
}
```

**syncRepositoryToDatabase 三步流程：**

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1. 正向扫描 | `scanSafDirectoryRecursive` / `walkTopDown` | 遍历物理文件，新增/更新 DB 记录 |
| 2. 反向清理 | `cleanupMissingPhysicalFiles` / `cleanupMissingLocalFiles` | DB 中活动记录对应物理文件不存在 → trash |
| 3. 去重保护 | `deduplicateDatabase` | 同 folder+fileName 重复记录仅保留最新 |

**防护机制：**
- 扫描前预加载回收站快照，跳过已 trash 的文件（防止"复活"）
- 跳过 `.` 开头的文件和目录
- 反向清理仅在 SAF 目录可访问时执行（防止误清）

### 4.3 GitManager

**源文件：** `data/git/GitManager.kt`

**职责：** JGit 操作封装，管理应用沙盒内的 Git 工作树。

**沙盒路径：** `context.filesDir/git_snippets_repo`

**关键方法：**

| 方法 | 功能 |
|------|------|
| `initOrClone(url, branch, pat)` | 本地无 .git 时 Clone 或 Init；有则更新 origin URL |
| `writeSnippetFile(snippet)` | 将单个片段写入沙盒工作树 |
| `removeSnippetFile(snippet)` | 从沙盒删除单个文件 |
| `exportAllSnippetsToDir(snippets)` | 批量将 DB 片段写入沙盒 |
| `cleanDeletedFiles(activePaths)` | 删除沙盒中不在 activePaths 集合的文件 |
| `commitAndPush(msg, url, branch, pat)` | git add . → git add -u → commit → push |
| `pull(url, branch, pat)` | git pull + 冲突自动备份 + reset --hard |
| `fetch(branch, pat)` | 仅下载远端对象，不修改工作树 |
| `getRemoteFileContents(branch)` | 读取 origin/branch 的 tree 对象获取远端文件内容 |
| `getSandboxFileContents()` | 遍历沙盒返回 relativePath→content 映射 |
| `getUncommittedChanges()` | git add + git status → 返回变更文件→类型映射 |
| `importGitDirToDatabase(dao)` | 遍历沙盒文件反向导入 DB |
| `getRepoLog(maxCount)` | 获取仓库级提交历史 |
| `getFileHistory(fileName, folder)` | 获取文件级提交历史 |
| `getFileContentAtCommit(commitId, path)` | 获取历史版本内容 |
| `getFileDiff(old, new, path)` | 行级 LCS Diff |

**文件过滤白名单：**
```
html, htm, js, jsx, ts, tsx, md, markdown, txt, text, json, xml, css, csv
```
单文件上限：2MB。

### 4.4 SyncEngine

**源文件：** `data/git/SyncEngine.kt`

**职责：** Git 同步的细粒度操作控制引擎。

**previewPull 对比逻辑：**

| 条件 | 判定 |
|------|------|
| 远端有、沙盒无 | ADDED (INCOMING) |
| 远端有、沙盒有但内容不同、DB 未改 | UPDATED (INCOMING) |
| 远端有、沙盒有但内容不同、DB 也改了 | CONFLICT |
| 远端无、沙盒有 | DELETED (INCOMING) |

**previewPush 流程：**
1. 触发 `syncWithLocalRepository`（物理→DB）
2. 触发 `exportAllToGit`（DB→沙盒 + cleanDeletedFiles）
3. 读取 `getUncommittedChanges`（git status）
4. 组装变更清单

**executePull 流程：**
1. 按用户选择解决冲突 → 写入沙盒
2. 记录 Pull 前沙盒文件列表
3. 执行 git pull
4. 计算远端删除差集
5. `syncGitFilesToDb`（沙盒→DB）
6. `syncAllToPhysicalStorage`（DB→物理 + 清理远端删除项）

### 4.5 SyntaxHighlighter

**源文件：** `util/SyntaxHighlighter.kt`（约 1000 行）

**职责：** 基于正则表达式的轻量级词法分析语法高亮引擎。

**工作原理：**
1. 接收原始代码文本 + 语言类型 + 明暗模式标志
2. 根据语言选择对应的正则规则集
3. 使用 `Pattern` 逐规则匹配，收集 (区间, 样式) 对
4. 通过 `buildAnnotatedString` 叠加 `SpanStyle` 生成富文本
5. 返回 `AnnotatedString` 供 Compose Text 渲染

**支持语言：** HTML, JS, CSS, JSON, Python, Markdown, Prompt, XML, YAML, Shell

**词法单元类型：** 关键字、字符串、数字、注释、标签、属性、函数调用、CSS 选择器/属性/单位、Markdown 标题/粗体/链接

**明暗适配：** 每种词法单元在 Light/Dark 模式下拥有独立色值定义。

## 5. 依赖注入与生命周期

### 5.1 AppContainer

**源文件：** `di/AppContainer.kt`

采用手动 DI + `by lazy` 惰性单例模式：

```kotlin
class AppContainer(private val context: Context) {
    val database: AppDatabase by lazy { AppDatabase.create(context) }
    val gitManager: GitManager by lazy { GitManager(context) }
    val snippetRepository: SnippetRepository by lazy {
        SnippetRepository(database.snippetDao(), database.folderDao(), context, gitManager)
    }
    val settingsDataStore: SettingsDataStore by lazy { SettingsDataStore(context) }
    val settingsRepository: SettingsRepository by lazy { SettingsRepository(settingsDataStore) }
}
```

**线程安全：** Kotlin `by lazy` 默认使用 `LazyThreadSafetyMode.SYNCHRONIZED`（双重检查锁）。

### 5.2 CompositionLocal 分发

```kotlin
val LocalAppContainer = staticCompositionLocalOf<AppContainer> { error(...) }
```

在 `SnippetStudioApp` 中通过 `CompositionLocalProvider` 注入，UI 层通过 `LocalAppContainer.current` 获取。

### 5.3 生命周期同步

`MainActivity` 中通过 `DisposableEffect` + `LifecycleEventObserver` 监听 `ON_RESUME`：
- 应用回到前台时自动触发 `syncWithLocalRepository`
- 检测外部文件变更并执行反向清理
- 通过 `DisposableEffect` 的 key（`repoTreeUri`）确保 URI 变更时重建 Observer

## 6. 关键算法说明

### 6.1 文件匹配策略（三策略级联）

**场景：** 物理文件扫描时，需将文件与 DB 已有记录匹配，避免产生重复条目。

**源文件：** `util/LocalFileManager.kt` → `findExistingSnippet()`

| 优先级 | 策略 | 匹配逻辑 |
|--------|------|----------|
| 1 | fileName 精确匹配 | `entity.fileName == fileName && folder 匹配` |
| 2 | defaultFileName 推导匹配 | 由 DB 记录的 title 推导默认文件名，与物理文件名比较 |
| 3 | title 规范化匹配 | 将空格/下划线统一后比较 title（含截断 20 字符变体） |

**folder 匹配规则：** `folder == null || entity.folder == folder || entity.folder.isBlank()`

### 6.2 沙盒镜像清理

**场景：** Push 前需确保 Git 沙盒精确反映 DB 当前状态。

**源文件：** `data/git/GitManager.kt` → `cleanDeletedFiles()`

**算法：**
```
输入: activeRelativePaths (DB 活动片段的 "folder/fileName" 集合)
遍历: 沙盒中所有受支持文件
判定: 若文件相对路径 NOT IN activeRelativePaths → 物理删除
结果: git status 可精准检测到 DELETED 状态
```

**熔断条件：** 仅当 `activeCount > 0 || trashedCount > 0` 时执行（防止全空仓误擦）。

### 6.3 ON_RESUME 生命周期同步

**场景：** 用户通过外部文件管理器删除/新增/修改文件后回到应用。

**源文件：** `MainActivity.kt`

**实现：**
```kotlin
val lifecycleOwner = LocalLifecycleOwner.current
DisposableEffect(lifecycleOwner, currentSettings?.repoTreeUri) {
    val observer = LifecycleEventObserver { _, event ->
        if (event == Lifecycle.Event.ON_RESUME) {
            // 触发 syncWithLocalRepository
        }
    }
    lifecycleOwner.lifecycle.addObserver(observer)
    onDispose { lifecycleOwner.lifecycle.removeObserver(observer) }
}
```

**设计要点：**
- 使用 `lifecycleScope.launch` 确保协程跟随 Activity 生命周期自动取消
- `DisposableEffect` key 包含 `repoTreeUri`，URI 变更时自动重建 Observer
- 同步在 `Dispatchers.IO` 执行，不阻塞 UI 线程

### 7.1 环境要求

| 项目 | 版本 |
|------|------|
| JDK | 17+ |
| Android Gradle Plugin | 8.x |
| Gradle | 8.x (Wrapper) |
| Kotlin | 2.x |
| minSdk | 30 (Android 11) |
| targetSdk | 35 |
| compileSdk | 35 |

### 7.2 构建命令

```bash
# Debug APK
./gradlew assembleDebug

# Release APK (需配置签名)
./gradlew assembleRelease

# Release AAB (上架 Google Play)
./gradlew bundleRelease
```

### 7.3 产出路径

| 类型 | 路径 |
|------|------|
| Debug APK | `app/build/outputs/apk/debug/app-debug.apk` |
| Release APK | `app/build/outputs/apk/release/app-release.apk` |
| Release AAB | `app/build/outputs/bundle/release/app-release.aab` |

### 7.4 签名配置

Release 构建需在 `app/build.gradle.kts` 中配置 `signingConfigs`：

```kotlin
signingConfigs {
    create("release") {
        storeFile = file("path/to/keystore.jks")
        storePassword = System.getenv("KEYSTORE_PASSWORD")
        keyAlias = System.getenv("KEY_ALIAS")
        keyPassword = System.getenv("KEY_PASSWORD")
    }
}
```

建议通过环境变量或 `local.properties` 注入敏感信息，避免提交至版本控制。

### 7.5 CI/CD

项目配置了 GitHub Actions 自动发布工作流（`.github/workflows/release.yml`），支持 Tag 触发自动构建与 Release 发布。
